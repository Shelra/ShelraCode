# Shelra Bench task ladder

This directory contains the current Shelra-first development suite. It is an
agent-harness benchmark: the subject being improved is Shelra, while the
model/provider is a recorded controlled variable.

The suite is intentionally more demanding than a smoke test. It progresses
from deterministic implementation work to an expert multi-step workflow:

| Task | Difficulty | Capability under pressure |
| --- | --- | --- |
| 01-input-normalization | easy | exact interpretation and basic verification |
| 02-config-pipeline | easy-medium | defaults, normalization, and integration |
| 03-ttl-cache | medium | time boundaries and state replacement |
| 04-retry-policy | medium-hard | retry, backoff, abort, and error semantics |
| 05-state-migration | hard | repair, compatibility, immutability, and rejection |
| 06-bounded-queue | hard | concurrency, order, failure isolation, and cancellation |
| 07-router-integration | very-hard | multi-file HTTP/API behavior |
| 08-workflow-orchestrator | expert | dependencies, scheduling, retries, skips, events, and cancellation |

The canonical suite is:

~~~text
bench/suites/shelra-agent-core-v0.2.json
benchmarkVersion: 0.2.0
suite: shelra-agent-core
oracleMode: benchmark-owned
~~~

## Task contract

Every task has:

- an immutable template workspace;
- visible tests for agent feedback;
- an explicit benchmark-owned acceptance contract;
- a deterministic external oracle in bench/oracles/;
- a fresh workspace copy for every run and task.

The runner copies a template to:

~~~text
.shelra/bench/runs/<runId>/tasks/<taskSlug>-<taskHash>/
~~~

The oracle receives that copied workspace as its working directory. Oracle code
stays outside the workspace the agent can edit. Visible tests are useful
feedback, but they are not the only grade.

Strict manifests must use oracleMode: benchmark-owned. Every criterion must
have a deterministic CheckSpec; the runner rejects a strict manifest that
does not. Criteria generated by the agent can help planning, but they are not
the authoritative benchmark oracle.

## Scoring

The current core policy is explicit and provisional:

~~~text
coding       0.45
intent       0.35
verification 0.20
correctness floor: coding >= 70
~~~

The score policy lives in the manifest and is versioned. The overall score is
N/A when required dimensions are missing. If coding is below the correctness
floor, overall is 0; efficiency cannot compensate for failed correctness.

Intent fidelity is criterion-level:

~~~text
passed  = 1.0
partial = 0.5
failed  = 0.0
not_run = 0.0
~~~

The host oracle and the agent's own verification are separate signals. A host
oracle pass does not prove that the agent verified its work. Missing provider
telemetry is N/A, never an invented zero.

## Agent adapters

`--agent shelra` (the default) runs every task through `Agent.processMessage()`,
the product's real turn loop: the same prompt, tool set, completion gate,
checkpoints, hooks, and memory an interactive or `--prompt` session uses. The
agent never sees the benchmark-owned checks; it must plan, implement, and
verify on its own, and the host grades the finished workspace afterwards. Its
verification score is the share of the task's own runnable checks (for example
`bun test`) that the agent executed successfully itself; hidden oracle commands
are excluded from that denominator.

`--agent shelra-autonomy` runs the older `AutonomyKernel` engine
(`--autonomous`). It is kept for comparison; its scores do not describe the
product path.

Each task records the per-step finish reasons and any upstream providers the
OpenRouter adapter quarantined in `finalResult`, so a run that failed because a
provider returned content-less steps is distinguishable from a model failure.

Oracle and test commands run under the runtime's process-tree memory ceiling
(6 GB by default) as well as their wall-clock timeout, because agent-written
code under test can allocate without bound; the tree is killed, the criterion
fails, and the run continues.

## Cross-session memory suite

`bench/suites/shelra-memory-v0.1.json` proves (or disproves) that persistent
project memory improves a later session. Phase A (`a-learn`) implements a
function whose tests depend on an undocumented generator script; phase B
changes the schema, which silently requires regenerating, and runs twice from
a copy of phase A's finished workspace: `b-recall-with-memory` keeps the
`.shelra/memory` and `.agents/skills` phase A produced, `b-recall-without-memory`
starts with them wiped. The oracle checks a hash of the schema embedded in the
generated module, so only a real regeneration passes. Manifest fields:
`workspaceFrom: "<task id>"` and `memoryPolicy: "keep" | "wipe"`. Each task's
`finalResult` records which memory entries retrieval expanded and which the
turn wrote, so a null result is attributable (nothing learned in A, or learned
but not retrieved in B). One run is one sample; repeat before concluding.

~~~text
bun run src/index.ts bench --manifest bench/suites/shelra-memory-v0.1.json --model <fixed-model>
~~~

## Public task set: aider polyglot

`scripts/build-polyglot-suite.ts` builds a suite from the public aider polyglot task set (Exercism
practice exercises curated by Aider-AI), pinned to one upstream commit. Fixtures, the shared
JavaScript test toolchain, and the generated manifest live in gitignored paths and are rebuilt on
demand:

    bun run scripts/build-polyglot-suite.ts --languages javascript,python --sample 16
    bun run src/index.ts bench --manifest bench/suites/polyglot-js-py-sample16-v0.1.json --max-cost 4 --json

Each task's prompt is the exercise's own instructions plus aider's directive naming the solution
files. The oracle (`bench/oracles/polyglot.ts`) restores every test file from the pristine fixture
before running the tests, so edited or deleted tests never count. JavaScript tests arrive upstream
with most cases skipped (`xtest`); the generator enables all of them, as aider's harness does.

Protocol difference, stated so nobody compares the wrong numbers: aider reports "pass rate 2"
(two attempts, test output fed back between them). Shelra's agent runs the tests itself inside one
session and may fix and re-run as often as its budget allows. A Shelra number on this set is a
single-session pass rate on the same tasks, not a leaderboard entry. Requirements on the host:
`node`/`npm` for JavaScript, `python` with `pytest` for Python. No Docker.

### Second trap: i18n catalog

`bench/fixtures/shelra-memory-v0.1/i18n-catalog` repeats the experiment in another domain: phase C
implements `t()` over a generated message catalog (`bun run build:messages`, discoverable only from
`package.json`); phase D adds a message to `locales/en.json`, which silently requires regenerating
the catalog. Without regeneration the visible tests stay green and `t("checkout.total")` returns
the key; the oracle checks the embedded catalog hash. Tasks `c-learn`, `d-recall-with-memory`,
`d-recall-without-memory` in the same manifest.

## Running a real benchmark

From the repository root, for a reproducible harness comparison, fix the model:

~~~text
bun run src/index.ts bench \
  --manifest bench/suites/shelra-agent-core-v0.2.json \
  --model <fixed-model>
~~~

On POSIX hosts, the shell wrapper is equivalent:

~~~text
./shelra-bench.sh \
  --manifest bench/suites/shelra-agent-core-v0.2.json \
  --model <fixed-model>
~~~

The runner creates and persists a new run before provider setup. It persists
each task as it completes and finalizes the run as completed, failed,
cancelled, or interrupted. Invalid configuration also leaves a visible
invalid run. Running the command twice creates two independent historical
records; it never overwrites the first one.

The model-policy free option is useful for a low-cost smoke run, but it can
select different free candidates between requests and runs. It is not suitable
for attributing an improvement to Shelra. Use an exact model for that.

Supported run controls include:

~~~text
--manifest <path>
--suite <name>
--agent <name>
--model <id>
--model-policy <policy>
--api-key <key>
--base-url <url>
--max-cost <usd>
--max-request-cost <usd>
--directory <dir>
--json
~~~

Keys and credentials are process inputs only and are never persisted.

## What is saved

Each run preserves:

- run ID, monotonic run number, timestamps, heartbeat, and status;
- benchmark version, suite, task count, seed, and sanitized configuration;
- agent, agent version, model, provider, and model version;
- Shelra version, repository commit, dirty state, and diff hash when available;
- operating system, runtime, and relevant tool versions;
- aggregate and per-task scores, resolved rate, tokens, cost, and durations;
- per-criterion pass/fail/partial/not-run outcomes;
- behavior counters, structured operational events, and artifact references;
- failure type and failure reason.

Large logs, diffs, screenshots, traces, and test output stay in artifact or
journal storage and are referenced from SQLite. Private chain-of-thought is not
stored.

## Eligibility and history

Every execution is historical, but not every historical record is eligible for
the primary leaderboard. A run must be finalized as completed, marked
leaderboard_eligible, and have a real overall score. Diagnostic smoke runs,
invalid runs, and incomplete runs remain visible in Run History but cannot
become leaderboard rows or baselines.

Latest, best, and baseline are different:

- latest is the newest compatible completed Shelra run;
- best is the highest recorded overall score in scope;
- baseline is an explicit selected compatible run and is not overwritten
  automatically.

See the [technical reference](../docs/design/shelra-bench-reference.md) for the
run lifecycle, schema, comparison rules, UI, scoring, reproducibility contract,
and current validation snapshot.

## HTML dashboard

To inspect the same persisted history in a browser:

~~~text
bun run bench:dashboard
open http://127.0.0.1:4173
~~~

Do not open `bench/dashboard.html` directly with `file://`: the HTML needs the
local server to read real SQLite data. The page reads the same persisted history
through the local dashboard server. It includes the run registry, Shelra version
timeline, comparison matrix, task detail, and an external-agent registry. Claude
Code, Codex, OpenCode, Goose, Aider, Cline, Roo Code, and Gemini CLI are shown as
calibration targets; they remain N/A until a real adapter writes a run for the
same benchmark contract.

## Oracle authoring rules

When adding a task:

1. Make the requirement materially harder or more diagnostic.
2. Add an immutable fixture under bench/fixtures/.
3. Add visible tests without making them the only grade.
4. Add a deterministic oracle under bench/oracles/.
5. Ensure the oracle fails the unmodified fixture.
6. Keep the oracle outside the agent-editable workspace.
7. Split the prompt into independently inspectable acceptance criteria.
8. Declare which dimensions are actually measured.
9. Bump benchmarkVersion when task semantics, oracle behavior, or scoring
   methodology changes.
10. Add persistence/comparison tests if the data contract changes.

Do not add a trivial task to inflate a score. Do not change historical results
in place.

## Current scope

The core ladder measures coding, intent, and verification, with agentic and
repair evidence available where the runtime records it. It does not yet claim
to measure memory, session resume, research quality, or statistically stable
multi-run confidence. Those need dedicated multi-turn protocols and task
families.
